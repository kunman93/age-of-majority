# Design

## Context

`.github/agents/reviewer.agent.md` lists checks 1-9 under "Check, in this order", followed by an empty "Project checks" section with a placeholder comment. Check 9 (Documentation freshness) already covers docs in general, but it does not name the AI instruction files, so a reviewer can easily treat them as out of scope. `.github/skills/openspec-*` and `.github/prompts/opsx-*` were generated by `openspec init` (commit `c4f65ba`) and never edited by hand. `openspec update` regenerates them and overwrites hand edits.

## Goals / Non-Goals

**Goals:**

- The reviewer reliably flags stale AI instructions, with a severity that matches check 9.
- `reviewer.agent.md` contains no template leftovers.

**Non-Goals:**

- Letting the reviewer fix instructions itself. Its independence depends on it staying read-only.
- Covering other instruction locations (for example `.github/copilot-instructions.md`). They do not exist in this repo.

## Decisions

### Numbered check 10 under "Project checks"

The new check goes under `## Project checks` as item `10.`, titled **AI instructions freshness**, in the same style as checks 1-9. Numbering continues the "in this order" sequence, so the reviewer runs it after check 9 and reports can cite it as "check 10".

Alternative considered: folding it into check 9. Rejected, because the Story asks for the placeholder to be replaced by the new check, and a separate item keeps the list of instruction paths visible.

### Severity: wrong is MAJOR, incomplete is MINOR

Instructions that misdescribe the repo (wrong command, stale path, removed step) are MAJOR. Instructions that are only incomplete (for example, a new npm script nobody mentions) are MINOR, which matches the existing MINOR level "docs that are thin rather than wrong". Agreed with the dev during research.

### Generated OpenSpec files point to `openspec update`

For `.github/skills/openspec-*` and `.github/prompts/opsx-*`, the suggested direction is to regenerate with `openspec update`. A hand edit would be lost on the next update. Agreed with the dev during research.

### Hard rules wording

"the test command, and the linter" becomes "the test and lint commands listed in check 7", which covers all four commands without repeating them.

## Risks / Trade-offs

- [The reviewer floods reports with MINOR "instructions incomplete" findings] → The check only triggers on changes to things the instructions describe, not on every diff.
- [`npm run test:bdd` writes `.features-gen/` and `test-results/`] → Both are git-ignored, which the existing rule in check 7 already allows.
