# Design

## Context

See proposal.md for motivation. Current state:

- The main session implements step 6 on Sonnet 5.5. A previous change removed delegating step 6 to a subagent because it lost the conversation context and saved nothing.
- Custom agents live in `.github/agents/` (`reviewer.agent.md` pins its model in frontmatter). Hand-written skills live in `.agents/skills/<name>/SKILL.md`; `.github/skills/openspec-*` is generated by `openspec update`.
- `.agents` and `.github` are in `.prettierignore`, so vendored Markdown is not reformatted and does not fail `format:check`.
- Official agent-facing sources exist: `greensock/gsap-skills` (MIT, `SKILL.md` format), `https://threejs.org/docs/llms.txt` and `https://r3f.docs.pmnd.rs/llms.txt`. three.js has no official skills.

## Goals / Non-Goals

**Goals:**

- Frontend knowledge is usable both by the main session in step 6 and by the `react-developer` agent, without duplication.
- GSAP and three.js guidance comes from official, current sources rather than training data.
- One set of engineering principles applies to every implementing agent, and it never justifies over-engineering.

**Non-Goals:**

- Measuring whether the output is "amazing". This change can only be verified structurally; the first frontend Story is the real test.
- Keeping vendored skills automatically in sync with upstream.

## Decisions

### Knowledge in skills, thin agent (option C)

The guidance lives in skills. Step 6 tells the main session to load them for UI, animation or 3D work, and `react-developer` loads the same skills.

Alternative considered (B): step 6 delegates frontend work to the `react-developer` subagent. Rejected for now for the same reason delegation was removed before: every fix round in steps 6 and 7 starts a fresh subagent that re-reads all context, and questions to the dev go through a relay. Upgrading to B later only changes step 6.

### Vendor 7 official GSAP skills unchanged

Copy `skills/gsap-{core,react,timeline,scrolltrigger,plugins,performance,utils}/SKILL.md` from `greensock/gsap-skills` at commit `aed9cfd3277740755f6bfc1155c7aa645403b760` byte for byte into `.agents/skills/<same-name>/SKILL.md`. Each vendored directory also gets the upstream `LICENSE` file unchanged, which satisfies the MIT notice requirement next to the copied file.

`.agents/skills/VENDORED.md` records the source repository, the pinned commit, the vendored skills, the skipped `gsap-frameworks`, and the update procedure (re-copy at a new commit, then re-run the byte comparison). It carries information that no file states otherwise, so it does not conflict with the "no restating" documentation rule.

`gsap-frameworks` is skipped because it covers Vue, Nuxt and Svelte. The vendored skills' cross-references to it are harmless.

Alternatives considered: all 8 skills (dead weight), our own condensed GSAP skill (stale knowledge to maintain), `npx skills add` (an extra tool whose target layout we do not control).

### `react-ui` skill

Hand-written, `.agents/skills/react-ui/SKILL.md`, triggered by UI, styling, layout, interaction or animation work in this repo. Contents:

- Stack facts that matter for decisions: React 19, TypeScript, Vite, Tailwind CSS 4, Vitest + Testing Library, Playwright-BDD.
- React reading of the engineering principles: SRP as small components and custom hooks, DIP through props and context, composition and compound components over configuration props, keep domain logic in plain TypeScript modules outside components (functional core).
- Non-negotiables: semantic HTML and keyboard access, visible focus, sufficient contrast, every animation honours `prefers-reduced-motion` (with GSAP via `gsap.matchMedia()`), animate transforms and opacity, lazy-load heavy assets, clean up on unmount.
- TDD for UI: Vitest + Testing Library for component behaviour (what the user sees and does, not implementation details); Playwright-BDD for user-visible outcomes; animations are asserted on their end state, with reduced motion making them deterministic; WebGL is not rendered in jsdom, so 3D is covered by Playwright (Chromium has WebGL) and by unit tests of the pure logic around it.
- Routing: for GSAP load the `gsap-*` skills, for 3D load `threejs`.

### `threejs` skill

Hand-written, `.agents/skills/threejs/SKILL.md`, triggered by 3D, WebGL, three.js, R3F or shader work. Contents:

- Before writing 3D code, fetch `https://threejs.org/docs/llms.txt` and `https://r3f.docs.pmnd.rs/llms.txt` and follow them over training data, flagging contradictions. Borrowed from the skepticism mandate of react.dev's `react-expert` skill, without its research machinery.
- Default: React Three Fiber + drei inside a `<Canvas>`; drop to raw three.js through refs only for what R3F does not cover. R3F v9 is the React 19 line.
- Rules: no React state updates in `useFrame` (mutate refs), reuse geometries and materials, dispose what R3F does not own, cap device pixel ratio, render on demand when the scene is static, `Suspense` with a fallback for loaded assets, a non-WebGL fallback and reduced-motion behaviour.
- GSAP with R3F: animate refs or `useFrame`-read values via `useGSAP`, never React state per frame.
- Installation commands for when a Story first needs 3D.

Alternative considered: vanilla three.js in effects, as in the dev's portfolio. Rejected as default because disposal and lifecycle wiring is manual and leak-prone in React; it stays available through refs.

### `react-developer` agent

`.github/agents/react-developer.agent.md`, frontmatter like `reviewer`: `name: react-developer`, a `description` that says when to use it, `model: Claude Sonnet 5.5`, `tools: ["read", "edit", "search", "execute", "web"]` (`web` to fetch the `llms.txt` sources and study reference sites).

Body: persona (creative frontend developer for this repo), it follows `AGENTS.md` (Working Style, Engineering Principles, TDD, atomic commits with the `git-commit` skill), loads `react-ui`, the relevant `gsap-*` skills and `threejs`, and a quality bar listing the reference sites from #25 as inspiration for feel and craft, not for copying content or assets. It verifies its work with the step 2 commands before reporting back. It does not restate the skills.

### `## Engineering Principles` in `AGENTS.md`

The section replaces `## Coding Style` in the same position, so it reaches the main session and every custom agent (custom agents also link to it explicitly rather than relying on inheritance). Every engineering rule gets exactly one home, and `## Working Style` keeps only how the agent collaborates with the dev (address, directness, asking instead of guessing, the 🙋 rule, permission outside the repo).

It opens with the priority rule: KISS and YAGNI win ties; a principle applies only when it makes the code simpler to change, test or read, and that must be explainable in one sentence. Then the list, grouped as code, design, architecture and quality level, as in the proposal. Language-specific readings belong in skills (`react-ui`), keeping `AGENTS.md` language-agnostic.

Where the existing rules land:

| Existing rule                                                   | From          | Lands in                       |
| --------------------------------------------------------------- | ------------- | ------------------------------ |
| Simplest solution, YAGNI, deletion over addition                | Working Style | Priority rule                  |
| Boring over clever                                              | Working Style | Priority rule                  |
| Follow conventions already present                              | Working Style | Code level                     |
| Prove behavior with executable validation                       | Working Style | Quality level (with TDD)       |
| No comments that restate the obvious; comment non-obvious "why" | Coding Style  | Code level (Clean Code)        |
| Never introduce secrets, tokens or credentials                  | Coding Style  | Quality level (secure by default) |

Alternative considered: keep `## Coding Style` and add the principles after it, with Clean Code pointing back. Rejected because two neighbouring sections would split one topic.

Onion/Hexagonal is reduced to its core idea (functional core, imperative shell; dependencies point inward). Full layering only once there is a real backend or several adapters, because for a single-page birthday card it would be the over-engineering the dev wants to avoid.

### Step 6 pointer

Story Workflow `#### 6. Implement` gets one bullet: for UI, animation or 3D work, load `react-ui`, the relevant `gsap-*` skills and `threejs`, and follow `## Engineering Principles`; the `react-developer` agent is available as a subagent when the dev asks for it. Bug fix and chore step 6 refer to the Story step 6, so they inherit it without edits.

## Risks / Trade-offs

- [Sonnet does not load the skills in step 6] → The explicit step 6 bullet plus trigger-rich skill descriptions. If it still happens, switch to option B.
- [Vendored GSAP skills go stale] → `VENDORED.md` pins the commit and documents the update; staleness is visible, not silent.
- [The `llms.txt` URLs move or change content] → The skill falls back to the official docs sites; the rules in the skill do not depend on them.
- [The principles become a checklist that drives over-engineering] → The priority rule comes first and requires a one-sentence justification; the reviewer can flag unjustified abstraction as a convention violation.
- [Frontmatter fields (`model`, `tools` aliases) are wrong and the agent silently loses capabilities] → Mirror the working `reviewer` frontmatter and check the agent is listed by the CLI.
